# STRIDE（旧 fitlog）設計書

作成日: 2026-11-04

## 1. 目的

筋トレ・ジョギング・体重を毎日手軽に記録し、目標に向けた変化や成長を
グラフ・カレンダー・お祝い表示で実感して、運動を続けられるようにする。

## 2. 前提・合意事項

| 項目 | 決定内容 |
|---|---|
| 公開方法 | GitHub Pages（Public リポジトリ `fitlog`）。GitHub Actions で main への push 時に自動デプロイ |
| 構成 | HTML / CSS / JavaScript（ES Modules）。ビルド不要 |
| データ保存 | ブラウザの localStorage のみ。サーバーには送信しない |
| 端末間のデータ | 共有しない。入力はスマホのホーム画面アプリに一本化し、PC へは JSON エクスポート／インポートで受け渡す |
| ライブラリ | Chart.js v4.5.0、canvas-confetti v1.9.3 をリポジトリ内 `lib/` に配置（オフライン動作のため） |
| 追加機能（v1.1.0） | 基礎代謝、カロリー目安、摂取カロリー、歩数（初版の対象外とし、④PWA化の後に追加） |
| プロフィール初期値 | 身長 165cm、年齢 52 歳、週の運動目標 3 日 |

## 3. 画面構成（下部タブ 5 つ）

| タブ | 内容 |
|---|---|
| ホーム | 現在体重・BMI・目標まで残り(kg)・開始時からの増減／目標達成日があれば残り日数と週あたり必要減量(kg)／今週の運動日数 / 目標日数、ストリーク／大きな入力ボタン（体重・筋トレ・ジョギング） |
| 記録 | 上部切替（体重／筋トレ／ジョギング）で入力フォーム。日付の初期値は今日。下に記録一覧（タップで編集・削除）。BMI・ペースは入力中に自動表示 |
| グラフ | 期間切替（1か月／3か月／1年／全期間）。体重（実測＋7日移動平均＋目標体重の破線とラベル）、筋トレ（種目選択→最大重量・推定1RM）、ジョギング（月別合計距離の棒＋平均ペースの線）。上部切替で「自己ベスト一覧」 |
| カレンダー | 月表示。筋トレ・ジョギングで色分けした印（両方の日は両方）。週の行の横にその週の運動日数、目標達成週は強調。ストリーク表示。前月・次月移動。日付タップでその日の記録 |
| 設定 | プロフィール・目標、種目の追加・削除、JSON エクスポート／インポート、CSV 出力、最終エクスポート日の表示。最下部「危険な操作」にサンプルデータ生成・全削除（確認ダイアログ付き） |

### 画面共通（2026-11-04 追加要望）

- 上部バーに「FITLOG」ロゴ・画面名・現在の日付と時刻（1 秒ごとに更新）を表示する。
- ホームの現在体重はグラデーションのカードで大きく表示する。
- 記録の日付は今日以前のみ入力できる（未来日の記録が「現在の体重」にならないようにするため）。

## 5. データ構造

localStorage キー `fitlog.v1` に以下の JSON を 1 つ保存する。

```json
{
  "schemaVersion": 1,
  "settings": { "heightCm": 165, "age": 52, "targetWeightKg": null,
                "targetDate": null, "weeklyGoalDays": 3, "lastExportAt": null },
  "exercises": ["ベンチプレス", "スクワット", "デッドリフト", "ラットプルダウン", "ショルダープレス"],
  "weights":  [{ "id": "…", "date": "2026-11-04", "weightKg": 70.2, "bodyFatPct": 22.1, "memo": "" }],
  "strength": [{ "id": "…", "date": "2026-11-04", "exercise": "ベンチプレス",
                 "weightKg": 60, "reps": 10, "sets": 3, "memo": "" }],
  "jogs":     [{ "id": "…", "date": "2026-11-04", "distanceKm": 5.0, "durationSec": 1800, "memo": "" }]
}
```

- 日付は `YYYY-MM-DD`（端末のローカル日付）。
- 体重は 1 日 1 件。同じ日付で保存すると上書き（確認表示あり）。
- 筋トレ・ジョギングは 1 日に複数件可。

## 6. 計算ルール

| 項目 | ルール |
|---|---|
| BMI | 体重(kg) ÷ (身長(m))²、小数 1 桁 |
| 開始時の体重 | 最も古い日付の体重記録 |
| 週あたり必要減量 | (現在体重 − 目標体重) ÷ (残り日数 ÷ 7)。残り日数 0 以下なら表示しない |
| ペース | 時間(秒) ÷ 距離(km) → 分:秒/km |
| 推定 1RM | Epley 式: 重量 × (1 + 回数 ÷ 30)。回数 1 のときは重量そのもの |
| 7 日移動平均 | 各記録日について、その日を含む直近 7 暦日内の記録の平均 |
| 週 | 月曜〜日曜 |
| 運動日 | 筋トレまたはジョギングの記録がある日 |
| ストリーク | 目標日数を達成した週が連続した数。今週は達成済みなら数に含め、未達でも途切れ扱いにしない（先週から数える） |

## 7. 自己ベスト判定

保存した記録を、それより前に保存されていた全記録（保存した記録自身を除く）と比較する。

| 対象 | ベスト条件 |
|---|---|
| 筋トレ（種目ごと） | 最大重量の更新、推定 1RM の更新 |
| ジョギング | 最長距離の更新、最速ペースの更新（3km 以上の記録のみ対象） |
| 体重 | 最低体重の更新、目標体重の達成（特別演出） |

- 判定は新規保存のときだけ行う（編集時は行わない。入力ミスの修正でお祝いが出ないようにするため）。
- 比較対象がない（その種目・区分の初回）場合は「初記録」と表示し、ベスト扱いにしない。
- 目標体重の達成: 開始時体重 > 目標体重 なら「体重 ≤ 目標」、開始時体重 < 目標体重 なら「体重 ≥ 目標」。
  過去に一度も達成していない場合のみ特別演出。
- メッセージ例:「ベンチプレス 自己ベスト更新！ 60kg → 62.5kg」
- 自己ベスト一覧は記録全体から都度計算する（削除・編集しても矛盾しない）。

## 8. PWA

- manifest.json: name「STRIDE 運動・体重・タスク管理」、short_name「STRIDE」（v1.2.0 で fitlog から改名）、display standalone、start_url/scope `./`、アイコン 192/512。
- iPhone 用に `apple-touch-icon` と `apple-mobile-web-app-*` メタタグ。
- バージョンは `js/version.js` の `APP_VERSION` に一元化し、ページ（設定画面の表示）と Service Worker（importScripts）の両方で使う。
- Service Worker: キャッシュ名 `fitlog-v<バージョン>`。アプリ一式を事前キャッシュ（HTTP キャッシュを使わず取得）。activate で旧キャッシュ削除。
- 取得方式: キャッシュ優先（なければネットワークから取得してキャッシュに追加）。画面遷移は index.html を返す。
- アプリに戻ってきたとき（visibilitychange）に更新を確認する。
  新しい SW が待機中になったら「更新があります」バナーを表示し、押すと skipWaiting → 再読み込み。

## 11. 食事・歩数とカロリーの目安（v1.1.0 で追加）

| 項目 | 内容 |
|---|---|
| 記録 | `daily: [{id, date, intakeKcal, steps, memo}]`。1 日 1 件（上書き確認）。摂取 kcal・歩数のどちらかは必須 |
| 設定 | `sex`（male / female / null）、`activityLevel`（low / normal / high、既定 normal）、`stepGoal`（既定 8,000） |
| データ形式 | schemaVersion 2。v1 のデータは読み込み時に `daily: []`・設定の既定値で補う |
| 基礎代謝 | 国立健康・栄養研究所の式（Ganpule ら, 2007）。男性 (0.0481W + 0.0234H − 0.0138A − 0.4235) × 1000 / 4.186、女性は定数 0.9708。係数は一般に引用されている値で、原典での確認は未了（要確認） |
| 身体活動レベル | 日本人の食事摂取基準（2025年版）の年齢区分別の値。18〜64 歳: 1.50 / 1.75 / 2.00、65〜74 歳: 1.50 / 1.70 / 1.90、75 歳以上: 1.40 / 1.70（「高い」は値なしのため 1.70）。二次情報で確認（要確認） |
| 消費の目安 | 基礎代謝 × 身体活動レベル |
| 摂取の目安 | 消費の目安 −（現在体重 − 目標体重）× 7,200 ÷ 目標達成日までの日数。目標達成日がなければ表示しない |
| 警告 | 摂取の目安が基礎代謝を下回るとき「無理な減量ペース」と表示 |
| 画面 | ホームに「今日のカロリー・歩数」カード、記録に「食事・歩数」、グラフに日別の摂取 kcal・歩数（目安・目標の破線つき）、カレンダーの日別記録にも表示 |
| 対象外 | 歩数の自己ベスト判定（お祝い表示）は入れない |

- STRIDE のタスクは端末単体で使う（同期なし）。自動同期は、社内規定で「暗号化すれば外部保存可」と確認できた場合に、暗号化同期（GitHub 非公開リポジトリ＋端末内 AES-256）として再検討する。
- GitHub Pages の保存領域はアカウント（tk1192-creator.github.io）単位で共通のため、同アカウントで他サイトを Pages に公開しない。

## 16. Face ID による画面ロック（v1.7.0）

| 項目 | 内容 |
|---|---|
| 方式 | パスキー（WebAuthn）を端末内で作成し、解除時に `navigator.credentials.get`（userVerification: required）で Face ID／パスコードの本人確認を行う。応答の認証器データの UV フラグも確認する |
| 目的と限界 | ロック解除済みの端末をのぞき見されないための画面ロック。保存データの暗号化は行わない（開発ツール等で localStorage を直接読むことは防げない）。サーバーがないため署名の検証は行わない |
| 対象画面 | STRIDE とタスク画面の両方（`js/lock.js` を両方の `<head>` で読み込み、表示前にロック） |
| ロックするとき | 起動時（新しいセッション）、アプリから離れて戻ったとき（すぐ／1／5／15 分。初期値 5 分。画面の行き来で誤ってロックしないよう 10 秒以内は対象外）、「今すぐロック」 |
| 設定の保存 | localStorage `stride.lock`（端末ごと）。解除状態は sessionStorage |
| パスキーの保存先 | 端末のパスキー保管場所（iPhone は iCloud キーチェーン）。記録データは送らない |
| 救済策 | パスキーを消した場合は、ロック画面の「解除できないとき」でパスキーを作り直す（作成時にも Face ID／パスコードの本人確認がある） |
| オフにするとき | 本人確認をしてから設定を削除 |
| 確認 | PC の Chrome で、パスキー作成・確認を代替関数に置き換えて動作確認。実機の Face ID は iPhone で要確認 |

## 18. 記録の保存先を GitHub 非公開リポジトリに変更（v2.0.0）

### 経緯（2026-11-05）
- 利用者が iPhone のホーム画面のアイコンを削除して追加し直したところ、記録がすべて消えた（ホーム画面アプリのデータはアイコンと一緒に消える）。
- 以前「追加し直しても記録は消えない」と案内していたのは誤りだった。
- 要望：「記録を別の場所で残しておく仕様に」。検討の結果「②-a GitHub を正にし、端末には一時的な写し＋タスクは自動バックアップ（送るかは選択）＋暗号化あり」に決定。

### 方式
| 項目 | 内容 |
|---|---|
| 保存先 | 非公開リポジトリ `tk1192-creator/stride-backup`。`data/records.enc.json`（記録）、`data/tasks.enc.json`（タスク。設定で選んだ場合のみ） |
| 正 | 記録は GitHub が正。端末の `fitlog.v1` は写し。`stride.cloud.state.dirty` が未送信の印 |
| 暗号化 | PBKDF2（SHA-256・310,000 回、ソルトはファイルに記録）で鍵を作り AES-256-GCM。鍵（raw）とトークンは端末の localStorage `stride.cloud` に保存 |
| 書き込み | 記録を変えたら 3 秒後に送信。GitHub Contents API に sha 付きで PUT。版が進んでいれば 409 → 読み直して統合 → 再送（最大 4 回） |
| 読み込み | 起動時、アプリに戻ったとき（15 秒以上空けて）、電波が戻ったとき |
| 統合 | 前回同期時の ID（base）を使う 3 者統合。両方にある記録は端末優先。片方にだけある記録は base になければ追加、あれば削除とみなす。体重・食事は 1 日 1 件（端末優先） |
| タスク | Task Board 本体は端末の localStorage のまま。変更があれば（ハッシュで判定）暗号化して上書きバックアップ。タスク画面では 1 分ごと・画面を離れるときにも同期 |
| 公開リポジトリの拒否 | 接続時にリポジトリが Private でなければ拒否 |
| 表示 | 上部バーの雲アイコン、設定の「記録の保存先（GitHub）」、未設定ならホームに注意 |
| 追加の注意表示 | iPhone の Safari で開いたら「ホーム画面の STRIDE とは別に保存される」と表示 |

### 確認
- 単体テスト 74 件（統合 7 件、暗号化 2 件、同期の流れ 12 件を追加。GitHub の代わりの受け口で、初回接続・自動送信・競合の統合・他端末の変更の取り込み・入れ直し後の復元・合言葉違い・トークン無効・オフライン・タスクのバックアップを確認）。
- 実際の GitHub で、空のリポジトリへの作成・sha 付き更新・古い sha での 409 を gh で確認（試験用ファイルは削除済み）。
- 既存の記録（v1.8.0 相当）が v2.0.0 でそのまま表示されることを確認。
- v1.8.0 の「タスクのデータ」の各ボタン（サンプル・テンプレート・CSV・インポートの確認画面）も確認し、同じ画面で #do= が変わったときに動かなかった不具合を修正。

## 21. 入力忘れのお知らせ・歩数の自動取り込み（v2.3.0）

### ① ショートカットでの時刻通知
- アプリの変更なし。手引き（8 章）に、iPhone の「ショートカット」のオートメーションで毎日 21:00 に通知する手順を記載（通知が使えない端末向け）。

### ② 歩数の自動取り込み
| 項目 | 内容 |
|---|---|
| 流れ | iPhone の「ショートカット」が「ヘルスケアサンプルを検索（歩数・今日）→ 統計（合計）」で歩数を求め、GitHub Contents API で保存先の `inbox/steps-YYYY-MM-DD-HHmmss.json`（`{"date","steps"}`）に PUT する |
| 取り込み | STRIDE は同期のたびに `inbox/` を一覧し、日付ごとに最新（ファイル名が最も新しい）の歩数を「食事・歩数」に反映（既存の食事の値は残し歩数だけ上書き）→ 暗号化した記録として保存 → 受け取り箱のファイルを削除 |
| トークン | 歩数用に別の Fine-grained token（同じ保存先・Contents Read and write）をショートカットに入れる |
| 注意 | 受け取り箱の歩数・日付は取り込まれるまで暗号化されない。ロック中はヘルスケアを読めない可能性（要確認）があるため、使う時間帯に実行する |

### ③ 入力忘れのお知らせ（Web プッシュ）
| 項目 | 内容 |
|---|---|
| 条件 | 21 時（日本時間）以降、その日の体重が未記録なら 1 日 1 回通知 |
| 送信 | 保存先リポジトリの GitHub Actions（`tools/notify/remind.yml` / `remind.mjs` を `.github/` に配置）。21:07・21:37・22:07 に実行（遅延・取りこぼし対策）、`notify/sent.json` で 1 日 1 回に制限。web-push（VAPID） |
| 鍵 | VAPID 鍵は保存先ごとに `tools/notify/setup_notify.py` で作成。秘密鍵は Actions のシークレット、公開鍵は `notify/vapid-public.txt`。管理者が自分で実行する（自動実行の安全確認で、シークレットへの書き込みは Claude からは行わない） |
| アプリ | 設定の「入力忘れのお知らせ」で通知を許可して購読し、`notify/sub-<端末ID>.json` に購読情報を置く。保存先に `notify/status.json` があれば、同期のたびに「最後に体重を記録した日付」だけを書く |
| 表示 | Service Worker の push で通知を表示、タップで STRIDE（記録画面）を開く |
| 条件 | iPhone はホーム画面に追加した STRIDE・iOS 16.4 以降。無効になった購読（404/410）は Actions が削除 |

### 確認
- 単体テスト 80 件（受け取り箱の取り込み、同じ日の最新を採用、受け取り箱の削除、通知の状態の書き込み条件と内容など）。
- 設定画面の表示、手引きの目次とスマホ幅の表示を確認。
- 実際の通知の送受信は、管理者が準備（setup_notify.py）を実行した後にテスト通知（workflow_dispatch）で確認する。
